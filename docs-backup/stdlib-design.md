# clux 标准库设计文档

## 设计原则

### 0. 尽量少用 FFI，尽量用源码实现（标准库以源码提供）

标准库秉承一个核心原则：**尽量使用少的 FFI，尽量使用源码实现**。

- **标准库以源码提供**——用户可见标准库源码，编译时纳入编译流程（而非预编译二进制链接）。
- **FFI 是最后手段**——只在以下情况使用 FFI：
  - 必须调用平台底层系统调用（socket/mmap/thread/...）——这些无法用 clux 源码复现。
  - 复用成熟的 C 库实现成本远低于重写（OpenSSL/PCRE/...）——重写易引入安全漏洞。
- **能用 clux 源码实现的就源码实现**——容器、算法、HTTP 协议、JSON/YAML、日期计算、位操作、字符串处理等，都用 clux 源码实现，不依赖外部 C 库。
- **理由**：
  - 源码可 CTFE 折叠（编译期计算优势），FFI 调用无法 CTFE。
  - 源码可移植（clux 编译到不同后端时源码随之编译），FFI 依赖目标平台的 C 库存在。
  - 源码可审计、可调试（用户可读标准库源码理解行为），FFI 是黑盒。
  - 减少 build 依赖（不强制用户安装 OpenSSL/PCRE/...才能用标准库核心功能）。

### 1. 不直接暴露 C/POSIX FFI，至少做封装

标准库不直接提供 C 或 POSIX C 标准库的 FFI 绑定，至少进行封装。理由：

- **利用编译期计算做运行时零开销校验**：clux 支持编译期计算（CTFE），可在封装层做大量编译期校验与转换，运行时零开销。
- **典型场景——`print` 的格式化字符串校验**：`print` 的 fmt 字符串与参数的匹配、格式化可在**编译期完成**（类似 C++ `std::format`）——fmt 与参数类型在编译期校验一致，格式化逻辑在编译期生成，运行时无解析 fmt、无运行时类型检查。
- **安全 + 零开销**：封装层既提供类型安全（编译期捕获 fmt/参数不匹配），又不引入运行时开销（校验全在编译期，运行时直接执行具体化代码）。

> **实现状态：📋 设计阶段**。本文档收集标准库设计 idea，不含实现计划。

### 2. 容器与算法泛型库，基于协议而非强约束

标准库提供一系列容器与算法函数，全部采用**泛型**的方式实现，通过**协议（protocol）而非强约束**解耦容器与算法。

- **泛型实现**：容器（Vec/Map/Set/...）与算法（sort/find/transform/...）全部用 M7 泛型实现，单态化产生具体类型/函数，运行时零开销。
- **协议而非强约束**：算法不绑定具体容器类型，而是基于**协议**（类似 C++ 迭代器协议）——算法作用于满足某协议的任意类型，容器通过实现协议接入算法库。
- **参考 C++ 迭代器协议**：C++ STL 算法基于迭代器协议（begin/end/++/*/==）解耦容器与算法，clux 可设计类似的协议体系（具体协议设计待后续，本轮只定概念）。
- **鸭子类型契合**：M7 泛型是无约束鸭子类型（§27），协议通过 `interface`（§31）做编译期结构检查，算法实例化时按实际类型检查操作是否支持——协议是"能力声明"，不是运行时多态。

> 具体协议（迭代器/范围/可比较/...）的语法与语义待后续设计，本轮只定概念方向。

### 3. C 标准库范围之外的平台封装模块

除 C 标准库范围（由 §1 的封装覆盖）外，标准库还需提供以下平台封装：

#### 3.1 时间日期计算（纯计算库）

- **纯计算库**，不是获取当前时间日期——只做日期/时间运算（加减、差值、时区转换、格式化/解析）。
- 获取当前时间走 §3.3 的平台 FFI，本模块只处理数值计算。
- 可在编译期求值（CTFE）——日期计算是纯函数，适合编译期常量折叠。

#### 3.2 正则表达式（内置 PCRE FFI）

- 内置 **PCRE** FFI 实现（编译时链接 PCRE 库）。
- 正则编译/匹配/捕获在运行时执行（PCRE 是 C 库），但正则字面量可在编译期编译为 PCRE 字节码（编译期校验语法、预编译 pattern）。
- 封装层负责内存管理（PCRE pattern/匹配上下文的生命周期绑定到 clux 所有权）。

#### 3.3 网络（底层 socket 平台 FFI，上层协议原生实现）

- **底层 socket**：通过平台 FFI 封装（POSIX socket / Winsock），提供统一的 socket 类型与操作。
- **上层协议**：HTTP 等基本协议**直接在标准库原生实现**（clux 代码，不依赖外部库）——HTTP/1.1 解析、请求/响应构造、客户端/服务器基础。
- 分层：socket FFI → 传输层（TCP/UDP 封装）→ 应用层（HTTP/...原生实现）。

#### 3.4 JSON / YAML 序列化（原生实现，依赖编译期反射）

- **本体直接实现**（clux 代码，不依赖外部库）——序列化/反序列化逻辑在标准库内。
- **与原生类型绑定依赖编译期反射**（反射机制还未设计）——自动序列化 struct 字段需要编译期反射获取字段名/类型/顺序。
- 反射未就绪前，可先支持手动序列化（用户实现 to_json/from_json 方法），反射就绪后支持自动派生。

### 4. 其他标准库模块（基于 C 标准库封装与新增）

#### 4.1 类 C 标准库封装（基础 API）

§1 的封装即覆盖 C 标准库范围，包括：
- 文件 I/O（fopen/fread/fwrite/...）、内存映射（mmap）——**§1 的封装范围**，不单列。
- 数学库（sin/cos/log/...）——**属于 C 标准库封装**（§1），CTFE 可常量折叠。
- 字符串处理（strchr/memcpy/...）——**属于 C 标准库封装**（§1）。

#### 4.2 高级文件系统模块（面向对象封装）

基于 §1 的基础文件 I/O API，增加**上层的面向对象封装**：
- 路径对象、目录遍历器、文件元信息对象等高级抽象。
- 路径拼接/规范化可在编译期常量折叠。
- 区分：§1 是 C API 的直接封装（函数式），本模块是上层 OO 抽象（类型 + 方法）。

#### 4.3 进程与环境（POSIX 封装）

- 基于 POSIX 库实现——进程启动/等待/信号、环境变量、命令行参数、退出码。
- Windows 平台走对应 Win32 API 封装（平台 FFI 分层）。

#### 4.4 并发原语

- 线程、互斥锁、条件变量、原子操作、一次性初始化。
- 系统编程必备，clux 无 GC + 所有权模型适合无数据竞争设计。

#### 4.5 错误处理基础设施（简单 Result）

- 提供简单的 `Result` 类型（`Result[T, E]`，泛型，单态化零开销）。
- clux 无异常（panic/return 错误值），`Result` 是错误值传递的标准容器。
- 不引入复杂的 monad 链式语法，保持简单——`Result[T, E]` + `if (r.is_err())` 风格。

#### 4.6 字符串处理（放在容器中实现）

- 字符串处理（分割/拼接/查找/替换/trim/UTF-8 编码）**放在 §2 容器库中实现**——字符串作为容器的特化，复用容器协议与算法。
- 不单列字符串模块。

#### 4.7 位操作与二进制协议

- 字节序转换、位域、二进制打包/解包（网络协议/文件格式处理）。
- 系统编程处理二进制格式必备。

#### 4.8 Crypto 模块（基于 OpenSSL）

- **统一 crypto 模块**，包含：
  - **随机数生成**——安全随机数（基于 OpenSSL RNG）。
  - **哈希**——MD5/SHA-1/SHA-256/SHA-512 等。
  - **基本加解密**——对称加密（AES/...）、非对称（RSA/...）、HMAC、签名/验签。
- **基于 OpenSSL 实现**——FFI 封装 OpenSSL，clux 侧管理密钥/上下文的生命周期（所有权绑定）。
- **顺便给 §3.3 网络加上 HTTPS 功能**——TLS 层基于 OpenSSL，HTTP 客户端/服务器可升级为 HTTPS。

#### 4.9 Logging 框架（只实现框架）

- **只实现框架**，不实现具体协议——日志级别、结构化日志字段、输出后端抽象。
- **业务侧编写较多代码填充协议**——具体输出后端（文件/syslog/network/...）由用户实现框架定义的接口。
- 定位：提供可扩展的日志骨架，不强制特定输出方式。

### 5. 特殊库

#### 5.1 反射库（std/reflect）——依赖反射机制设计

- **利用泛型对反射结果进行封装**——反射产出的类型/字段/方法信息用泛型容器与类型封装，提供类型安全的反射 API。
- **先记录，待反射机制设计后细化**——clux 的反射机制尚未设计（§3.4 JSON/YAML 的自动序列化也依赖反射），反射库的具体 API 形态取决于反射机制本身的形态。
- 反射库是反射机制的"用户侧封装"——反射机制是编译期/运行期能力，反射库是基于该能力的标准库接口。

#### 5.2 编译库（std/build）——依赖 C 后端完成

- **基于文件系统 / 子进程 / builtin 函数封装的库**——提供在 clux 代码内触发编译的能力。
- **改变编译流程的触发方式**：
  - 现状：driver 的 run/build 直接触发编译流程。
  - 目标（模块场景）：`cli → 执行模块的 build 脚本 → 调用 builtin 函数触发编译文件/模块`。
  - 即：编译不再是 driver 硬编码流程，而是由模块的 build 脚本（clux 代码）通过 std/build 库驱动——build 脚本调用 std/build 的 builtin 函数触发编译。
- **等 C 后端完成后再设计**——std/build 依赖编译为可执行文件后能自举运行 build 脚本的能力，C 后端是前提。
- 定位：类似 Rust 的 build script（build.rs）机制——构建逻辑用 clux 本身编写，标准库提供编译驱动 API。
